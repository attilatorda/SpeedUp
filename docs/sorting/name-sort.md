# Name sort

A bucket sort for person names. The bucket boundaries come from character
frequency tables: one for characters anywhere in a name, and one each for
the 1st, 2nd and 3rd position. The bucket sizes follow from the input size
and the sizes those tables predict.

Code: `src/algorithms/sort/name_sort.c`. Tables: `src/algorithms/sort/name_freq_tables.h`,
generated by `codegen/name_tables/build_name_tables.py`.

## Related work

| Algorithm | Idea | How name sort relates |
|-----------|------|-----------------------|
| ProxmapSort (Standish) | a map function predicts each key's final region | the trie lookup plays the map function |
| Learned Sort (Kristo et al., SIGMOD 2020) | a model of the key CDF, trained on a sample, puts each key near its final position | the frequency tables are a CDF model of name prefixes |
| Burstsort (Sinha & Zobel, 2004) | a trie of string prefixes with buckets at the leaves that "burst" into subtries when full | name sort's trie is a burst trie, but cut in advance from the tables and a sample instead of at run time, and at most 3 levels deep |
| MSD radix sort, multikey quicksort (Bentley & Sedgewick, 1997) | distribute on one character at a time | name sort finishes every bucket of more than 32 names with MSD radix sort |

## Why positions 1, 2 and 3

Person names are very unevenly distributed. In the 2010 US Census surnames,
weighted by how many people carry them:

- The first letters range from 9.6 % (M) and 9.4 % (S), through B 8.5 %,
  C 7.7 % and H 7.1 %, down to Q 0.24 % and X 0.04 %. Equal-width buckets on
  the first letter would range from nearly empty to huge.
- Some prefixes are heavy on their own: Ma 3.0 %, Mc 1.7 %, Wil 1.3 %,
  Mar 1.2 %, Smi 0.95 %, Joh 0.83 %, Sch 0.78 %. Splitting heavy prefixes on
  their 2nd and 3rd letter evens out the buckets.

## Data

Public domain, US Census Bureau, downloaded once by the generator:

- 2010 surnames: 162,253 surnames with counts (`Names_2010Census.csv`)
- 1990 first names: 4,275 female and 1,219 male first names with frequencies

The SSA baby-name files were the first choice, but ssa.gov refuses plain
downloads. The mix is half surnames and half first names, written in title
case ("Smith", "Mary"), as people type them. The tables count bytes,
symbol 0 being the end of the name. The generator also writes the name lists
to `benchmarks/datasets/names/`, and `benchmarks/datasets/capture_names.py`
draws synthetic "Surname Firstname" lists from them.

## Algorithm

1. **Sample.** n/128 names, at least 256 and at most 16,384, taken at even
   strides and sorted.
2. **Plan.** A trie over the first 3 symbols. The root covers all names.
   - For each symbol c at the next position, the share of names is
     estimated as `(sample hits + 16 · prior[c]) / (sample names + 16)`.
     The prior is that position's table, mixed 99:1 with the any-position
     table so that no byte gets exactly zero.
   - A child expected to hold more than `target` (32) names, and seen in the
     sample at least once, becomes a node of its own (a 257-entry block).
   - Children that are not split share a leaf with their left neighbour,
     while the two together stay under `target`.
   - The leaves, in order, are packed into buckets of about `target` names.
   - Each bucket records how many leading bytes all of its names share.
3. **Distribute.** Walk the trie for every name (at most 3 table lookups),
   count the names per bucket, take prefix sums and scatter.
4. **Finish.** Buckets of up to 32 names get an introsort, larger ones an MSD
   radix sort. Both start after the bucket's shared bytes. MSD radix sort
   bounds the cost of a misjudged bucket by the bytes it reads.

Below 131,072 names step 4 is all there is: MSD radix sort on the whole
input (see Tuning).

The order is byte order, or with `SPEEDUP_NAME_SORT_ASCII_CASELESS` A–Z
folded to a–z and ties broken by bytes. Bucketing and comparing use the same
folding, so the buckets stay in order.

## Tuning

These measurements decided the constants. Setup: AMD Ryzen 5 2600X, GCC 13.2
`-O2`, synthetic "Surname Firstname" lists (`capture_names.py`), median of 5
or 11 runs. The machine varies by 10–15 % from run to run.

**Trie depth.** Deeper tries cut buckets closer to the target but are
slower. At 1M names (ns per name):

| depth | split at | buckets | largest bucket | ns/name |
|------:|---------:|--------:|---------------:|--------:|
| 3 | 1 × target | 2,965 | 13,314 | 124.6 |
| 4 | 4 × target | 10,488 | 9,238 | 148.1 |
| 8 | 4 × target | 17,229 | 7,379 | 170.9 |
| 8 | 1 × target (block cap hit) | 11,028 | 94,795 | 169.7 |

Each level is another 1 KB block lookup, and with thousands of blocks those
lookups miss the cache. MSD radix sort on a large bucket is cheaper than a
deeper trie that would have avoided it. The 3 positions of the original
design are the fastest choice.

**Finishing buckets.** MSD radix sort for every bucket above 32 names beats
introsort for buckets up to 8 × target: 117.5 against 124.6 ns/name at 1M,
and 108.0 against 127.7 at 100k.

**Sample size.** n/16 and n/128 measure the same within the noise. n/128 is
the default because it costs less at small n.

**Where planning pays.** Name sort against a plain MSD radix sort (the
benchmark's own, on `std::string_view`):

| names | std::sort | MSD radix | name sort (planned) |
|------:|----------:|----------:|--------------------:|
| 10,000 | 106.5 | 56.7 | 87.4 |
| 100,000 | 154.9 | 89.5 | 96.0 |
| 200,000 | 247.1 | 108.9 | 105.4 |
| 500,000 | 329.2 | 163.3 | 118.1 |
| 1,000,000 | 378.0 | 198.6 | 121.0 |

Below 131,072 names, name sort is the MSD radix sort alone.

**Correction from the clean ablation** (the paper's study, every config against
MSD radix sort in the same interleaved run, idle machine). With planning forced
at every size, name sort overtakes MSD radix sort:
- from about 500,000 names on the synthetic lists, not 100k–200k;
- from about 50,000 on the multilingual list;
- never on the 162,253 Census surnames.

So the crossover depends on the names. A threshold derived from the sample
would fit better than the fixed 131,072, which is a next step.

**Do the frequency tables help?** The prior weight was set to 0 (sample
only), 16 (default) and 10⁹ (tables only), in two interleaved rounds of 11
runs each. At 1M names: 129.3 / 131.8 / 134.3 ns in round one, and 130.9 /
119.1 / 117.0 ns in round two. The differences are within the noise. On
Census-like names, a 1 % sample already finds the heavy prefixes, and the
tables alone are just as good. The tables matter where the sample is thin:
- rare prefixes, which the sample may miss entirely;
- the 256-name minimum sample;
- inputs where `sample_size` is set low on purpose.

Planning with the tables alone and no sample is the obvious next
experiment for streaming input.

The clean ablation confirms this for English names: sample only, default and
tables only are within about 5 % of each other on the synthetic and Census
lists. On the multilingual list the tables alone are about 30 % slower than the
default, and the sample alone about 16 % slower. The difference comes from the
prior acting as smoothing for rarely sampled prefixes, not from knowledge of
names. Results: `docs/papers/sorting/` and
`benchmarks/outputs/namesort_ablation_*.csv`.

## Real name lists

The tuning above used synthetic "Surname Firstname" pairs: real names at real
frequencies, but randomly paired, and drawn from the same data as the
tables. `benchmarks/datasets/census_name_lists.py` builds real lists:
- the 162,253 Census surnames themselves, in five orders (shuffled,
  popularity rank, sorted, reversed, ALL CAPS);
- 1M multilingual names from `capture_listing.py intl`.

Results are in [results.md](results.md#name-sort-on-real-name-lists). Each
list was checked against qsort in byte and caseless order, and all were
correct.

- **On real surnames, the plan does not pay at this size.** Name sort is
  1.6–3.2× faster than `std::sort` but 1–39 % slower than plain MSD radix
  sort (shuffled: 75.7 against 62.2 ns, 22 % slower). 162k names are just
  above the 131,072 threshold. Unique surnames are short and differ early,
  so MSD radix sort finishes them in a few cheap passes. The crossover
  depends on the data: for full names it lies between 100k and 200k; for
  bare surnames it is above 162k, the whole list, so where exactly is not
  measured.
- **Input order and case cause no pathologies.** Sorted, reversed, popularity
  order and ALL CAPS input all behave. In byte order the title-case priors
  do not fit ALL CAPS names, and the sample takes over.
- **Multilingual, 1M names:** 144.7 ns against 182.7 for MSD radix sort
  (1.26×) and 386.9 for `std::sort` (2.67×). 79 % of the names are
  non-ASCII, which the US tables do not cover, so the sample did all the
  work. The small vocabulary gives large buckets (up to 17k names), and MSD
  radix sort finishes them.

## Unicode

- **Code point order** works today. Name sort treats names as bytes, UTF-8
  byte order is code point order, and multi-byte characters just occupy
  more trie positions. The Census tables only know ASCII, so for non-ASCII
  names the sample does the work.
- **Language order** (Hungarian á after a, cs after c; German ä with a) is a
  collation question, not a sorting one. Make collation keys first: ICU
  `ucol_getSortKey`, or `strxfrm`/`std::collate::transform` (see
  `benchmarks/qt_stack/icu_collation_key.h`). Then name-sort the key bytes.
  Collation keys are byte strings whose `memcmp` order is the locale's
  order, so the algorithm is unchanged. Only the priors stop applying,
  because key bytes are not letters, and the sample takes over.
- **Built-in priors for other alphabets** need name-frequency data per
  language (for example the Hungarian given-name registry, or national
  surname statistics). The generator is written so that a second table set
  is one more data source.

Both are later steps.
