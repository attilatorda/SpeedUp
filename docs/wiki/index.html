SpeedUp

SpeedUp is a cross-platform library of fast algorithms and data structures, written in C and C++ with optional assembly and GPU paths. Every accelerated path has a portable fallback, so the library always works, and its C ABI is stable so other languages can bind to it.

What is in it

ComponentWhat it doesInterface
Binary searchBranchless and batched lower-bound search, measured from L1 to DRAMC
BucketizationSwitches a list between sort orders in O(n), sorting only the rows on screenC++17, Java 17
SortingRadix, bucket and bitonic sort, which no standard library shipsC, C++17
Name sortA bucket sort for person names, planned from name-frequency tablesC, C++17

  • Papers: the three studies behind the components.

Platforms

  • Windows and Unix, x86-64 and ARM64 (64-bit).
  • Compilers: GCC, Clang and MSVC, C11 and C++17.
  • Dispatch order: CUDA, then OpenCL, then optimized CPU code, then the C fallback. The GPU backends are stubs today, so every call ends on the CPU.

Getting started

Build and test

SpeedUp builds with CMake 3.20 or newer.

bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build --output-on-failure

The test suite has four programs: binary search, Bucketization, the sorts (C) and the sorting C++ layer. Optional dependencies (NASM, Qt 6, ICU, GLib, GTK 4) only add benchmarks; when they are missing, CMake skips those targets.

For the language bindings, build a shared library:

bash
cmake -S . -B build-shared -DBUILD_SHARED_LIBS=ON
cmake --build build-shared --config Release

Use it from CMake

cmake
add_subdirectory(SpeedUp)
target_link_libraries(my_app PRIVATE speedup)                 # C ABI: search, sorts
target_link_libraries(my_app PRIVATE speedup::bucketization)  # header-only C++17

A first program

c
#include <stdint.h>
#include "speedup/api.h"

int main(void) {
    speedup_init();
    int64_t a[5] = {2, 4, 6, 8, 10};
    int64_t idx = speedup_binary_search_i64(a, 6, 5);   /* 2 */

    double v[4] = {3.5, -1.0, 2.0, 0.0};
    speedup_radix_sort_f64(v, 4, NULL);                  /* -1, 0, 2, 3.5 */
    return idx == 2 ? 0 : 1;
}

MinGW on Windows

If a test program exits with code 0xc0000139 (entry point not found), the loader picked up another toolchain's libstdc++ DLL. Put the bin folder of the GCC that built SpeedUp first in PATH before running the tests.

Overview

Architecture

Layers

SpeedUp has two kinds of components.

  • Algorithms behind the C ABI. Binary search and the sorts are plain C functions with fixed-width types. They dispatch to the best backend at run time and fall back to portable C. Any language with a C FFI can call them.
  • Header-only C++ and native ports. Bucketization calls back into user code (key functions, comparators), so it is a C++17 header library with a native Java port instead of a C ABI.

Dispatch

Dispatch order: CUDA, then OpenCL, then optimized CPU code, then the C fallback. Callers can steer it:

c
speedup_set_backend_preference(SPEEDUP_BACKEND_FORCE_CPU);
speedup_set_cache_hint(hint);       /* the binary search picks its kernel from the L2 size */
speedup_sort_set_simd(0);           /* bitonic sort without its AVX2 kernel */

The CUDA and OpenCL backends only check for a runtime today, so every preference ends on the CPU. Bitonic sort is the sort meant to gain a GPU path first. CPU features are detected once (src/core/cpu_features.c), and the AVX2 kernels are built in their own translation unit with AVX2 enabled.

Algorithms

Binary search

Header: include/speedup/algorithms/binary_search.h. Kernels: src/algorithms/binary_search/bsearch_kernels.h.

What the library does

  • Single keys use a branchless search while the array fits the L2 cache hint, and a branchless search that prefetches both candidates of the next step beyond it. Branchy code loses to mispredictions in cache, and plain branchless code loses to memory latency outside it.
  • Many keys (*_batch_*) search 16 keys in lockstep, so their cache misses overlap. On arrays larger than the caches this is about 4× faster per key than calling the single-key function in a loop.
c
int64_t pos = speedup_lower_bound_i64(sorted, key, n);      /* first index with sorted[i] >= key */
speedup_lower_bound_batch_i64(sorted, n, keys, count, out); /* many keys at once */

All functions take an array sorted in ascending order. For keys that occur more than once, speedup_binary_search_i64 returns the first occurrence.

How it was chosen

The study measured 22 variants from 8 KiB to 512 MiB in throughput and latency mode, with two compilers. It also found the error in the original benchmark: its keys came from rand(), which never exceeds 32,767, so the large-array results never left the first 256 KiB. The hand-written assembly and AVX2 searches of the prototype are kept in legacy/ for the comparison only. See Papers and docs/papers/binary-search/.

Algorithms

Bucketization

Fast re-sorting for collections that can be ordered in several ways, such as a file manager's name, size and date columns. Header-only C++17 (include/speedup/bucketization.hpp, target speedup::bucketization) and pure Java 17 (bindings/java/bucketization/).

How it works

  1. Sort keys. Each way of ordering is a sort key. It maps every element to a 64-bit order-preserving key (numbers exactly, strings by their first 8 bytes), or it is just a comparator.
  2. Bucket layout. For each key a sample is sorted and cut into buckets of planned, unequal sizes. The first and last buckets are one page long, so the first screen in either direction is cheap.
  3. Pre-sorting. When an element is added, it picks its bucket for every key once: a binary search over a few split points.
  4. Switching the order is a counting pass over the bucket ids: O(n), with no comparisons. Switching back to a key used before costs O(1).
  5. Lazy sorting. A bucket is sorted the first time a position inside it is read. Showing the first page sorts about one page of elements.

The order is exact. Buckets only decide when an element gets sorted, never where it ends up.

Example

cpp
#include "speedup/bucketization.hpp"
namespace bz = speedup::bucketization;

struct File { std::string name; std::int64_t size; std::int64_t modified; };

bz::BucketIndex<File> files(bz::BucketPlan::defaults().with_page_size(visible_rows));
files.add_sort_key(bz::SortKey<File>::of("name", &File::name));
files.add_sort_key(bz::SortKey<File>::of("size", &File::size));
files.add_sort_key(bz::SortKey<File>::of("modified", &File::modified));
files.add_all(load_directory());            // pre-sorting happens here

files.sort_by("modified", bz::Direction::descending);   // O(n), no comparisons
for (const File& f : files.range(first, first + visible_rows)) draw(f);

Costs

OperationCost (n elements, k buckets, p page size)
add one elementO(keys × log k)
sort_byO(n + k), or O(1) when the grouping is cached
first pageabout O(p log p)
remove_if / update_ifO(n) per call
memory per key and element8 B key + 2 B bucket id, plus 4 B for a cached grouping

Limits

  • Not thread-safe.
  • Below about 2,000 items a plain sort is just as fast.
  • One bucket plan per index, not per sort key.

Full design and the cross-language specification: docs/bucketization/README.md. Measured in the sort code of KDE Dolphin, the GNOME file managers, Qt file managers, terminal file managers and the Godot editor: docs/bucketization/benchmarks.md and the paper.

Sorting

Sorts that the standard libraries of C, C++, Java, Python, Rust, Go, C# and JavaScript do not ship. All of them sort in ascending order and in place. Header: include/speedup/algorithms/sort.h. C++ layer: include/speedup/sort.hpp.

SortTypesUse it for
Radix sort (LSD)u32, i32, f32, u64, i64, f64Large numeric arrays: linear time, no comparisons
Bucket sortu64, i64, f64Numeric data with a smooth distribution
Bitonic sortu32, i32, f32, u64, i64, f64Small arrays and fixed-pattern sorting: no data-dependent branches
Name sortbyte stringsPerson names and other strings
Bitonic merge sort (0.3.1)u32, i32, f32, u64, i64, f64Large numeric arrays: bitonic blocks, AVX2 merges

Order

  • Integers: numeric order.
  • Floating point: IEEE 754 totalOrder, -NaN < -inf < … < -0.0 < +0.0 < … < +inf < +NaN. Values are moved, never changed, so NaN payloads survive.
  • Names: byte order (UTF-8 code point order), or ASCII-caseless with SPEEDUP_NAME_SORT_ASCII_CASELESS.

Examples

c
double v[N];
speedup_radix_sort_f64(v, N, NULL);         /* NULL: the library allocates scratch */
speedup_bucket_sort_f64(v, N, scratch);     /* or pass N elements of scratch */
speedup_bitonic_sort_f64(v, N);             /* in place, no scratch */
cpp
#include "speedup/sort.hpp"
namespace ss = speedup::sort;

ss::radix_sort(values);                      // std::vector<int|long|size_t|float|double|...>
ss::radix_sort_by_key(files, [](const File& f) { return f.size; });  // stable, any movable type
ss::name_sort(names);                        // std::vector<std::string> or std::string_view

Every function sorts. If an allocation fails, it falls back to an in-place comparison sort.

How they work

  • Radix sort: 8-bit digits. One read pass builds every digit's histogram, and a digit on which all keys agree is skipped. Signed and floating-point keys are encoded to unsigned in place and decoded on the last copy.
  • Bucket sort: 64 equal-depth segments from a sample of 1,024 keys, each cut into equal-width buckets of about 32 keys, then an introsort per bucket. A bad estimate only makes a bucket larger. It never makes the result wrong.
  • Bitonic sort: every comparator puts the smaller key first. That makes the network exact for any n without padding, because comparators that reach past the end are skipped. An AVX2 kernel is chosen at run time.

The GPU path (0.3.1)

Bitonic sort can run on an OpenCL GPU. SpeedUp opens the OpenCL loader at run time, so building needs no OpenCL SDK, and machines without a GPU stay on the CPU.

c
speedup_set_backend_preference(SPEEDUP_BACKEND_FORCE_OPENCL);  /* always on the GPU, if there is one */
speedup_bitonic_sort_u32(keys, n);
speedup_set_backend_preference(SPEEDUP_BACKEND_AUTO);          /* default: the GPU from 65,536 keys */

The keys are copied to the GPU and back on every call. Any GPU error falls back to the CPU.

When to use which

  • Radix sort beats std::sort on large integer and floating-point arrays. It is slower on input that is already sorted, which std::sort handles very cheaply.
  • Bitonic sort with AVX2 beats std::sort on 32-bit keys while they fit in the caches. Beyond that, its O(n log² n) work loses.
  • Bucket sort is about level with std::sort on this machine. It is kept for data whose distribution a sample describes well.

Algorithms

Name sort

A bucket sort for person names. The bucket boundaries come from character-frequency tables of real names, one for each of the first three positions, built from US Census data and refined on a sample of the input.

c
speedup_str_t names[M];          /* {data, len}; need not be NUL-terminated */
speedup_name_sort(names, M, SPEEDUP_NAME_SORT_BYTES);
speedup_name_sort(names, M, SPEEDUP_NAME_SORT_ASCII_CASELESS);

Why it can work

Names are far from uniform. About 9.6 % of US surnames begin with M and 0.04 % with X, and prefixes such as Ma, Mc and Wil hold more than one percent each. Knowing where the dense regions are lets the sort cut buckets of equal expected size in one step.

Algorithm

  1. Sample n/128 names (256 to 16,384) and sort them.
  2. Plan a trie of at most three 257-entry lookup tables per path. A prefix expected to hold more than 32 names gets a child table for the next position; light symbols share leaves. The leaves are packed into buckets of about 32 names.
  3. Distribute in two linear passes, with at most three lookups per name.
  4. Finish each bucket: insertion sort or introsort up to 32 names, MSD radix sort above. Both skip the bytes the bucket's prefix fixes.

Below 131,072 names, planning does not pay, and name sort is its MSD radix sort alone.

What the measurements say

  • On a million synthetic "Surname Firstname" names it is about 3× faster than std::sort and faster than a plain MSD radix sort.
  • On the 162,253 real Census surnames it is about 3× faster than std::sort but slower than plain MSD radix sort, because short unique surnames suit MSD radix sort.
  • The frequency tables did not measurably beat the input sample alone, and deeper tries, with more even buckets, were slower.

Unicode

UTF-8 already sorts correctly, in code point order. For language order (Hungarian cs after c, German ä with a), sort ICU or strxfrm collation keys with the same function. The sample then does the work the ASCII-only tables cannot.

Design notes: docs/sorting/name-sort.md. Study: docs/papers/sorting/.

Bucket plans (class BucketPlan, immutable). defaults() is geometric(64, 2.0). Options: with_page_size, with_max_buckets, with_symmetric, with_sample_size, with_seed, with_rebalance_skew, with_auto_rebalance.

Benchmarks

Every benchmark checks its results against a reference before it times anything, and raw results are kept as CSV files in benchmarks/outputs/. The reference machine is an AMD Ryzen 5 2600X under Windows 10, with GCC 13.2 and MSVC 19.41.

Where the numbers are

Bucketizationbenchmarks/*_stack/ (Dolphin, GNOME, Qt, terminal, Godot)bucketization_*.csvdocs/bucketization/benchmarks.md
Sortingbenchmarks/sort/bench_sort.cppsort_ryzen2600x_*.csv, namesort_*.csvdocs/sorting/results.md

The sorting results also come as an interactive page with charts and tables: benchmarks/outputs/sort_benchmarks.html.

Headline results

  • Binary search: 16 interleaved searches are about 4× faster per key than single searches once the array outgrows the caches.
  • Bucketization: in the sort code of real file managers, switching the sort column drops from hundreds of milliseconds to a few milliseconds on folders of about 100,000 entries.
  • Sorting: radix sort is up to about 4× faster than std::sort on large 32-bit arrays. Name sort is about 3× faster on large name lists.
  • 0.3.1: bitonic merge sort is about 3.4× faster than std::sort on 32-bit keys. Bitonic sort on a GPU (GeForce GTX 1660 SUPER, copies included) is about 14× faster on 16 Mi 32-bit keys when it runs back to back, and about 5× when the GPU has been idle and has to clock up first.

Running them

bash
python benchmarks/scripts/run_bsearch_benchmarks.py run --build build --label gcc
python benchmarks/scripts/run_bucketization_benchmarks.py --build build
python benchmarks/scripts/run_sort_benchmarks.py datasets data
python benchmarks/scripts/run_sort_benchmarks.py run --build build --label gcc --data data

Method

  • Pin the thread to one core and raise its priority.
  • Interleave the timed runs of the algorithms round-robin, so slow periods of the machine hit them all alike.
  • Report the median and the interquartile range.

Compare algorithms within one run. Separate runs on the reference machine differ by up to about 15 %.

Language bindings

SpeedUp exposes a stable C ABI for bindings. Build it as a shared library (-DBUILD_SHARED_LIBS=ON) and load it with your language's FFI.

Status

Most bindings are stubs today. A binding counts as smoke-complete when it loads the shared library and gets the expected result from speedup_binary_search_i64.

Python, through ctypes

python
import ctypes
from ctypes import c_int64, POINTER

lib = ctypes.CDLL(path_to_speedup_dll)

Contributing

Workflow

  1. Create a feature branch.
  2. Keep commits focused and descriptive.
  3. Build and run the tests before opening a pull request.
bash
cmake -S . -B build
cmake --build build --config Release
ctest --test-dir build --output-on-failure

Rules

  • The C API stays stable and backward-compatible.
  • Every accelerated path keeps a working fallback when the accelerator is missing.
  • Tests compare against a reference implementation (qsort, a linear scan), not against hand-picked expected values.
  • Performance changes come with benchmark evidence: the harness, the hardware, the compiler, and the CSV in benchmarks/outputs/.

Changelog

All notable changes to SpeedUp. Versions follow Semantic Versioning; while the major version is 0, a new minor version may change APIs.

0.3.1 - unreleased

Bitonic hybrids, and the first GPU path.

Added

  • Bitonic sort on the GPU (OpenCL): speedup_bitonic_sort_* runs on an OpenCL GPU under SPEEDUP_BACKEND_FORCE_OPENCL, and under SPEEDUP_BACKEND_AUTO from the size where the GPU wins with its copies included. The OpenCL loader is opened at run time, so building needs no OpenCL SDK and machines without a GPU stay on the CPU. Work-groups sort blocks in local memory, then global and local merge stages finish the network. speedup_opencl_available(), speedup_opencl_device_name().
  • Bitonic merge sort (speedup_bitonic_merge_sort_*): blocks sorted by the bitonic network, then merged, first inside the L2 cache and then across the array, with an AVX2 merge that merges a vector of keys at a time in registers.
  • Bitonic bucket sort (speedup_bitonic_bucket_sort_*): the sampled bucket sort with every bucket finished by the bitonic network; 32-bit types too.
  • C++: bitonic_merge_sort, bitonic_bucket_sort. Benchmark entries bitonic_merge, bitonic_bucket, bitonic_gpu; tuning runner run_sort_benchmarks.py tune031.

Fixed

  • speedup/backend/dispatch.h lacked extern "C", so C++ code calling the dispatch hints did not link.

Unreleased

Sorting, first step: sorts that the standard libraries of C, C++, Java, Python, Rust, Go, C# and JavaScript do not ship (docs/sorting/README.md).

Added

  • Radix sort (LSD, 8-bit digits, skips digits all keys share) for u32, i32, f32, u64, i64 and f64: speedup_radix_sort_*.
  • Bucket sort (sampled equal-depth segments, interpolated buckets) for u64, i64 and f64: speedup_bucket_sort_*.
  • Bitonic sort for any n, with an AVX2 kernel chosen at run time: speedup_bitonic_sort_*, speedup_sort_set_simd.
  • Name sort, a bucket sort for person names, with buckets cut from character-frequency tables for positions 1–3 (US Census data) refined on a sample: speedup_name_sort, speedup_name_sort_ex, speedup_name_compare (docs/sorting/name-sort.md).
  • C++17 layer include/speedup/sort.hpp, including a stable radix_sort_by_key for any movable type.
  • Table generator codegen/name_tables/build_name_tables.py, name lists benchmarks/datasets/names/, synthetic name lists benchmarks/datasets/capture_names.py.
  • Tests tests/unit/test_sort.c and test_sort.cpp, benchmark benchmarks/sort/bench_sort.cpp, results docs/sorting/results.md and benchmarks/outputs/sort_*.
  • Wiki docs/wiki/: Markdown pages built into one self-contained site (docs/wiki/build_wiki.py), with search, a C and C++ API reference, a summary of every version, and light and dark modes.
  • Paper docs/papers/sorting/ (arXiv-ready), with the study runner benchmarks/scripts/run_sort_benchmarks.py (main runs, real name lists, an ablation of name sort's design choices) and benchmarks/scripts/sorting_paper_numbers.py (every number, table and figure).

0.3.0 - unreleased

Binary search, measured properly. The earlier benchmark drew its keys with rand(), which never exceeds 32,767, so it never searched beyond the first 256 KiB of an array; its large-array results did not hold. A new harness measures 22 variants from 8 KiB to 512 MiB, and the library now uses what won.

Added

  • speedup_lower_bound_i64, speedup_binary_search_batch_i64 and speedup_lower_bound_batch_i64. The batch functions search 16 keys in lockstep: about 4× faster per key than single searches on arrays larger than the caches.
  • Benchmark harness benchmarks/binary_search/bench_bsearch.cpp (throughput and latency modes, every variant verified before and during timing), runner benchmarks/scripts/run_bsearch_benchmarks.py, results benchmarks/outputs/bsearch_ryzen2600x_*.csv.
  • Papers, with every number generated from the result files: docs/papers/binary-search/ and docs/papers/bucketization/ (docs/papers/build_papers.py builds them and packs them for arXiv).
  • legacy/README.md: what the prototype files are and why their results do not hold; the disassembly of the prototype's lost *_fixed functions.

Changed

  • speedup_binary_search_i64 used the textbook search on every path. It now uses a branchless search, with prefetching once the array exceeds the L2 cache hint (speedup_set_cache_hint): about 2× faster in the caches, and never more than a few percent slower than the textbook search on large arrays. When the key occurs more than once, it now returns the first occurrence.
  • speedup_cpu_has_avx2 detects AVX2 (it returned 0).
  • A forced CUDA or OpenCL preference no longer makes the search return -1 (neither backend implements it yet).
  • benchmarks/core/benchmark_win.c draws its keys with SplitMix64; -DBENCH_LEGACY_RAND restores the old generator.
  • The Bucketization benchmarks build on Windows (nnn's entry struct used POSIX-only types); run_bucketization_benchmarks.py --tag keeps the results of other machines apart, carries on when a benchmark reports invalid orders, and reads CSVs with CRLF line endings. Summary timings now cover valid orders only. Windows results: docs/bucketization/benchmarks.md.
  • speedup_check_strxfrm: checks that strxfrm() orders like strcoll(). The Windows C runtime does not in its English locales, which makes nnn's name key unusable there.
